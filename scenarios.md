# Сценарии AI Chat Platform

Ответственность компонентов описана в [README](README.md). Ниже потоки из обсуждения актуальной схемы. Открытые решения указаны рядом со сценариями.

## 1. Регистрация и подтверждение почты

1. Web отправляет `POST /auth/register` без JWT. Запрос идёт в Identity. На входе применяется rate limit.
2. Identity валидирует данные, проверяет уникальность email, хеширует пароль, создаёт аккаунт `pending_verification` и выпускает одноразовый код. В той же транзакции сохраняет в outbox задачу отправки письма и событие `UserCreated`. Web получает `202 Accepted` и показывает форму ввода кода.
3. Задача уходит в очередь `Email Notifications`. Notifications передаёт письмо через API внешнего Email Provider. Ответ провайдера подтверждает приём на отправку. Если нужен статус доставки, его можно получать отдельным webhook.
4. Web отправляет `POST /auth/verify-email` в Identity. Identity проверяет код, срок жизни и число попыток. При успехе погашает код, активирует аккаунт и выдаёт JWT для автологина. Правильный код подтверждает доступ к почте.

## 2. Назначение Free

1. Identity публикует `UserCreated` в `User Events`. Событие содержит `event_id` и `user_id`.
2. Subscription асинхронно создаёт `user_subscriptions(user_id, plan_id)` с тарифом по умолчанию из своей БД. Сейчас это `FREE`. `plan_id` ссылается на локальную таблицу `plans`, где находятся `FREE`, `PRO` и их лимиты. `user_id` — внешний идентификатор из Identity. На одного пользователя приходится одна текущая запись. Повторное событие оставляет существующий тариф как есть.
3. Если первое сообщение приходит до обработки события, Subscription возвращает `subscription_pending`. Web показывает ожидание подготовки подписки.

## 3. Логин и авторизация запросов

1. `POST /auth/login` идёт по публичному маршруту `Web → Identity`. На входе применяется rate limit. Identity проверяет учётные данные, подтверждение почты и статус аккаунта, после успешного входа выдаёт токены. Обновление токена идёт в Identity.
2. Web отправляет короткоживущий access token в `Authorization: Bearer …`. На входе проверяются подпись, издатель, срок действия и назначение JWT. BFF прокидывает его дальше в сервисы в пределах общей границы доверия API платформы.
3. Сервисы проверяют JWT локально, извлекают `user_id` из `sub` и проверяют доступ к своим данным. Например, Chat & Agent проверяет владельца чата.

Для начальной версии выбрали передачу JWT. Рассматривали доверенные заголовки от аутентифицированных сервисов, онлайн-проверку токена в Identity и OAuth Token Exchange для выдачи отдельных прав downstream-сервисам. Мгновенная блокировка уже выданного JWT остаётся отдельным требованием.

## 4. Первый экран, профиль и пароль

- `GET /bootstrap` идёт по пути `Web → BFF`. BFF параллельно читает профиль из Identity, список последних чатов из Chat & Agent, текущий тариф и остаток квоты из Subscription. У нового пользователя список чатов пустой. Имя и аватар берутся из профиля.
- Экран аккаунта читает профиль через BFF из Identity. Изменение имени и других полей профиля обрабатывает Identity, он же обновляет свою БД.
- Смена пароля из аккаунта идёт по защищённому маршруту `Web → Identity`. Identity проверяет текущий пароль, сохраняет хеш нового пароля в своей БД. Восстановление забытого пароля обсуждалось как отдельное действие, его поток пока не определён.

## 5. Открытие чата и отправка сообщения

1. Web открывает существующий чат и читает историю отдельным `GET`. В новом диалоге пустой экран можно показать сразу, а чат сохранить при первом сообщении. HTTP-контракт первого сообщения, когда `chatId` ещё отсутствует, предстоит уточнить.
2. В существующий чат Web отправляет `POST /chats/{chatId}/messages` с JWT по пути `Web → Chat & Agent`. Chat & Agent проверяет владельца чата и резервирует квоту до запуска генерации.
3. Chat & Agent сохраняет сообщение, запускает Agent Runtime и возвращает `text/event-stream` в ответ на тот же POST. На входе SSE проксируется без буферизации. Web читает поток из ответа `fetch`.
4. Agent Runtime передаёт промпт, модель и ограничение выхода в LLM Connector. Connector вызывает внешний Inference Provider по HTTPS, передаёт поток и нормализует итоговый `usage`. Chat & Agent сохраняет ответ в истории. При наличии изображений файлы хранятся в S3, ссылки на них принадлежат истории чата.

Чат хранит историю диалога. Запуск агента обрабатывает одно новое сообщение. Состояние обычного запуска живёт в процессе. Поток `POST → SSE` выбран по аналогии с [наблюдавшимся маршрутом веб-чата ChatGPT, § OA.1.3](https://borowiecki.dev/pdf/2607.07652).

## 6. Резерв, списание и исчерпание квоты

Subscription хранит лимит и счётчики `used_tokens` и `reserved_tokens` по пользователю и периоду. Доступный остаток равен лимиту за вычетом списанного и зарезервированного. Для начала учитываем `input_total + output`. Например, 900 входных токенов, включая 600 чтений из кэша, плюс 200 выходных дают списание 1 100.

1. **До SSE** Chat & Agent собирает полный промпт с историей и определяет размер резерва по объёму входа и лимиту выхода. Синхронный `reserve(run_id, amount)` атомарно проверяет и резервирует остаток в Subscription. Так параллельные чаты используют общий лимит пользователя. Строгий лимит требует верхней границы расхода. При приблизительном подсчёте входа возможен перерасход.
2. **При отказе в резерве** Chat & Agent возвращает `429` с `quota_exceeded`. Web по этому коду показывает окно апгрейда. SSE ещё не открыт.
3. **После генерации** Connector передаёт фактический `usage`. Для запуска сохраняются `input_total`, `cache_read`, `output`, списанная сумма и `cache_write`, если провайдер передал эту детализацию. У OpenAI кэш уже входит в `input_tokens`. У Anthropic полный input складывается из обычного входа, чтения и записи кэша. [OpenAI Responses](https://developers.openai.com/api/reference/resources/responses/methods/create) · [Anthropic Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)
4. Chat & Agent сохраняет фактический `usage` и синхронно вызывает `settle(run_id, usage)`. Subscription одной транзакцией списывает фактический расход и освобождает резерв. Если было зарезервировано 1 500 и списано 1 100, доступный остаток увеличится на 400. При таймауте повторяется тот же `settle` с тем же `run_id`. Расход учитывается один раз. [Паттерн частичного списания резерва](https://docs.tigerbeetle.com/coding/two-phase-transfers/)

`reserve` и `settle` — две локальные транзакции в БД Subscription. Генерация и доставка SSE происходят между ними. Общего коммита на весь сценарий нет. Политика для запуска без итогового `usage` и резервирование нескольких LLM-вызовов в одном агентном цикле пока открыты.

## 7. Покупка Pro

1. `Web → BFF → Subscription` возвращает текущий тариф и каталог. Пользователь выбирает `PRO`.
2. Web отправляет `POST /invoices` с `plan_id` по пути `Web → BFF → Subscription`. Subscription берёт цену из каталога и создаёт `invoice` со статусом `pending`. В счёте хранятся `invoice_id`, `user_id`, `plan_id`, сумма и валюта.
3. `Subscription → Payment Connector → Payment Provider` синхронно создаёт внешний платёж. Subscription связывает `provider_payment_id` со счётом. Web получает `invoice_id`, `checkout_url` и срок действия ссылки, если его отдаёт провайдер. Повторный запрос к провайдеру для того же счёта использует тот же ключ идемпотентности. Пользователь вводит платёжные данные на странице провайдера. [Пример внешней страницы оплаты](https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process)
4. После оплаты **`Payment Provider → Subscription`** передаёт входящий HTTPS webhook. Это отдельный запрос от провайдера спустя время. Subscription проверяет подлинность подтверждения, идентификатор платежа, сумму и валюту, затем в одной транзакции помечает счёт `paid` и включает `PRO`. Повторное уведомление безопасно. [Пример webhook `payment.succeeded`](https://yookassa.ru/developers/using-api/webhooks)
5. После возврата на сайт Web читает статус своего счёта через `GET /invoices/{invoiceId}` по пути `Web → BFF → Subscription`. Источник подтверждения — webhook провайдера, обработанный Subscription. Если нужно письмо об оплате, `SubscriptionActivated` можно записать в outbox транзакции активации.
6. Перед окончанием подписки Subscription ставит задачу в `Email Notifications`. Notifications отправляет напоминание через Email Provider.

## 8. Встроенный веб-поиск

1. Agent Runtime передаёт модели описание инструмента `web_search(query: string)`. Модель предлагает вызов со свободным текстовым запросом.
2. Chat & Agent выполняет `web_search`. Он синхронно обращается к Yandex Search API через Tool Proxy и приводит выдачу к формату инструмента. Результат инструмента может содержать заголовки, URL и фрагменты текста.
3. Agent Runtime передаёт результат модели через LLM Connector в следующем вызове. Ответ продолжает идти в Web по тому же SSE-потоку.

## 9. Подключение пользовательских MCP-серверов

1. Пользователь добавляет HTTPS URL в настройках. Chat & Agent хранит конфигурацию подключения в своей БД (`user_id`, `connection_id`, URL, ссылка на учётные данные). Для защищённого сервера используются учётные данные этого подключения.
2. При подключении MCP-клиент в Chat & Agent вызывает `tools/list` через Tool Proxy и показывает доступные инструменты. Перед первым вызовом модели в запуске Agent Runtime загружает актуальные описания включённых инструментов, учитывая срок действия кэша подключения.
3. Когда модель выбирает внешний инструмент, Agent Runtime разрешает имя в конкретное подключение. MCP-клиент вызывает `tools/call` по пути `Chat & Agent → Tool Proxy → External MCP Servers`. Результат получает модель. Браузер продолжает читать SSE чата.
4. Для `2026-07-28` Streamable HTTP работает без `initialize` и `Mcp-Session-Id`. Если инструменту нужно состояние между вызовами, он возвращает явный идентификатор вроде `browser_id`. Модель передаёт его в аргументах, обвязка отправляет запрос. Если на запуск всегда есть ровно один такой объект, обвязка может подставлять ID сама. [MCP 2026](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
5. Если понадобится поддержка `2025-11-25`, MCP-клиент выполняет `initialize` при первом обращении в рамках запуска. При получении `Mcp-Session-Id` клиент держит его в памяти реплики и добавляет в заголовок следующих запросов. Общее хранилище сессий понадобится только при отдельном требовании продолжать ту же сессию между запусками или после смены реплики. [MCP 2025](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports#session-management)

В варианте развёртывания `Tool Proxy` находится внутри `Kubernetes namespace: ai-chat`, пользовательские MCP-серверы — за его границей. `NetworkPolicy` разрешает Chat & Agent нужные внутренние связи и внешний MCP-трафик через Tool Proxy. Tool Proxy ограничивает сетевые назначения для пользовательских URL. [Kubernetes NetworkPolicy](https://kubernetes.io/docs/concepts/services-networking/network-policies/)
