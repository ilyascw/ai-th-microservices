# Лог архитектурных решений

## v0.1 — исходная схема

Схема из коммита `601481b` принята как точка отсчёта v0.1. На ней есть BFF перед API Gateway, два пересекающихся обозначения Agent Service, общий CRUD для Auth и Subscription, отдельные хранилища контекста и файлов, Redis и S3.

## v0.2 — схема контейнеров

| Изменение | Почему |
| --- | --- |
| Убрали BFF, оставили API Gateway. | У BFF нет отдельной обязанности в текущем MVP. Gateway маршрутизирует запросы и пропускает SSE-поток агента клиенту. |
| Объединили чаты и выполнение агента в Chat & Agent Service. | Один сервис владеет историей чата и запускает обычный агентный цикл при новом сообщении. Чтение истории не требует запуска агента или обращения к другому сервису. |
| Заменили два кружка агента одним прямоугольником. | На уровне контейнеров изображён один сервис; параллельная обработка разных чатов не требует дублировать его на схеме. |
| Вместо Context_DB и Redis показали хранилище Chats. | История чата нужна уже сейчас. Отдельный checkpointer и Redis не нужны для обычного цикла «LLM → tool → LLM»; их добавят при конкретном требовании к восстановлению незавершённых запусков или обмену событиями между процессами. |
| Оставили изображения в S3, убрали отдельное хранилище файлов. | Пока поддерживаются только изображения, связанные с сообщениями чата. Метаданные и ссылки на объекты принадлежат Chat & Agent Service. |
| Убрали общий CRUD и совместное владение Users. | Identity Service владеет данными пользователей и учётными данными, Subscription Service — подписками. Сервис подписок хранит `user_id`, но не пишет в хранилище Identity. |
| Привели имена к единому стилю и убрали суффикс `_DB`. | Сервисы названы по назначению с суффиксом `Service`, а тип хранилищ уже виден по форме блока. |
| Разделили схему пунктирными сетевыми границами. | Отдельно показаны клиентская зона, пограничный API Gateway, внутренние сервисы и внешние провайдеры. Подписи к границам и стрелкам убраны, чтобы сохранить аскетичный стиль исходной схемы. |
| Решили заменить актора User на прямоугольник Frontend. | На диаграмме контейнеров показываем компонент, который обращается к API Gateway; пользователя как актора оставляем для диаграммы System Context. |
| Развели пересекающиеся стрелки. | Связи между компонентами легче проследить на схеме. |

### Отложенные решения

- Шина событий: Identity Service сообщает об удалении и блокировке пользователя; заинтересованные сервисы обновляют собственные данные. До появления шины способ обработки удаления аккаунта остаётся отдельным проектным решением.
- Anti-Fraud Service: выявляет подозрительную активность; статус пользователя меняет Identity Service.
- Долговечное восстановление агентного цикла: выбрать checkpointer и хранилище, когда появится сценарий паузы или восстановления незавершённого запуска.

## v0.3 — сценарии платформы и схема контейнеров

| Изменение | Почему |
| --- | --- |
| Добавили Web BFF за API Gateway. | Первый экран собирает профиль, список чатов, тариф и остаток квоты. Регистрация и потоковая генерация идут из Gateway напрямую в профильные сервисы. |
| Добавили `User Events`, `Email Notifications` и сервис Notifications. | Subscription назначает Free по событию `UserCreated`. Письмо с кодом подтверждения отправляется независимо от HTTP-запроса регистрации. |
| Зафиксировали синхронный резерв и списание токенов через Subscription. | Параллельные чаты используют общий остаток. После генерации списывается фактический расход, который LLM Connector приводит к общему формату. |
| Уточнили потоковое API чата. | Веб отправляет сообщение через Gateway и получает SSE в ответ на тот же POST. История чата загружается отдельным запросом. |
| Показали внешний checkout и входящий платёжный webhook через Gateway. | Страница провайдера принимает платёжные данные. Subscription активирует Pro после проверенного подтверждения провайдера. |
| Вывели внешний поиск и пользовательские MCP-серверы через Proxy. | Web Search обращается к Yandex Search API, а Chat & Agent обращается к MCP-серверам пользователей. Proxy задаёт точку контроля для исходящих HTTPS-вызовов. |
| Описали девять пользовательских и межсервисных сценариев в [scenarios.md](scenarios.md). | Для каждого потока видны участники, порядок вызовов и решения, которые предстоит уточнить. |
